Part A — Software Requirements Specification (SRS) 
1. Purpose 
This SRS defines what PatientPathly Web is expected to do at the product level. It describes user roles, modules, screens, actions, 
field-level CRUD, workflows, authorization, integrations, error behavior, non-functional requirements and acceptance criteria. The 
companion SDD translates these requirements into a proposed technical design. 
2. Product scope 
REQUIRED PRODUCT SCOPE: PatientPathly is a healthcare platform for public patients and healthcare organization users, 
supporting multiple clinics/branches under an organization. The required feature areas are OPD management, appointment 
scheduling, inpatient management, emergency (ER), laboratory (LIS), radiology and imaging, pharmacy management, billing and 
payments, inventory management, patient portal and mobile app, HR and staff management, reports and analytics, security and 
compliance, multi-clinic/multi-branch administration, and telemedicine/virtual care. The existing approved technology direction is 
React + Node.js/Express + PostgreSQL. Maps/Places/geolocation and email are the only previously confirmed third-party integration 
categories; additional integrations must be specified and approved. 
SOURCE BASELINE: the uploaded architecture defines tenant-aware users, organizations, roles, permissions, scoped role 
assignments, sessions and append-only audit logs. It recommends deny-by-default authorization, backend enforcement, tenant-
scoped repositories, role/permission cache invalidation, and audit logging. 
PROPOSED: patient-facing discovery is a public-facing capability that allows users to search nearby participating facilities using 
location consent or a manually entered area. It should not expose patient locations or clinical records. 
3. Goals 
• Give patients a clear way to discover nearby participating healthcare facilities and request or manage appointments, subject to 
approved workflows. 
• Give authorized staff tools to manage patient registration, appointments, clinical records, laboratory workflows and billing. 
• Support organization-level administration with multiple branches, departments and scoped staff access. 
• Enforce permissions consistently in the UI and API, with the API/database access layer authoritative. 
• Provide traceable requirements so each requirement maps to screens, actions, permissions, endpoints, data entities and tests. 
• Make third-party integrations configurable, resilient to provider failures, and limited to the approved services.

9. Button/action specification rules 
All buttons must have a defined outcome, permission, validation behavior, loading state, success feedback and failure feedback. 
Destructive or irreversible actions require confirmation. Buttons must not be the only authorization boundary; the API repeats the 
relevant permission and scope checks. 
Action class Expected behavior 
Create / Save Validate required fields and formats; disable duplicate submission while 
pending; persist through API; show field -level errors; on success navigate to 
detail/list and refresh affected data. 
View / Open Fetch by identifier through a scoped endpoint; return not -found or forbidden 
without leaking cross-tenant existence. 
Edit / Update Load current values; validate changes; reject immutable/signed fields; show 
conflict if the record changed concurrently where optimistic locking is used.  
Archive / Deactivate Show confirmation and impact; preserve referential integrity; require permission; 
record actor/time/reason where appropriate. 
Delete Physical deletion only for approved non-sensitive draft/configuration records 
with no dependencies. Clinical, billing and audit records default to 
void/archive/amendment rather than hard delete. 
Reschedule / Cancel Validate state transition, schedule rules and branch scope; persist status 
change; trigger only approved notifications. 
Sign / Verify Require elevated permission; confirm action; preserve signer/verifier identity and 
timestamp; prevent silent edit after finalization. 
Export Check export permission server-side; apply identical filters/scope; avoid 
including fields not permitted; audit export metadata.  
Use my location Request browser geolocation only after explicit user action; show 
denial/unavailable/timeout state and manual location alternative.  
Save role permissions Save complete mapping transactionally; validate delegability; audit before/after 
mapping; invalidate authorization cache.

11. Core business workflows 
11.1 Sign-in and authorization 
1. User submits credentials. 
2. API validates credentials, account status, organization status and session state; rate limiting applies. 
3. API issues a session/token using the approved secure-cookie strategy and returns user context. 
4. Frontend requests the effective authorization profile and renders permitted routes/actions. 
5. Every protected API repeats permission, scope and policy checks; a hidden UI button does not grant access.

6. On role/scope changes, sessions/authorization versions and cached permissions are refreshed or revoked according to policy. 
11.2 Branch-scoped patient registration 
7. Staff selects an active branch from the branches available in their authorized scope. 
8. Frontend requests patient creation form metadata; the server determines organization context from the authenticated session. 
9. Staff submits patient demographics and any required consent/identifier fields. 
10. API validates fields and verifies that all referenced branch/department IDs belong to the same organization. 
11. Patient record is created in a transaction; actor, branch context and timestamp are recorded. 
12. System returns the patient identifier and navigates to the patient detail page if access is still authorized. 
11.3 Appointment lifecycle 
13. Authorized user searches eligible patients, facilities, doctors and available appointment times. 
14. User selects a patient, branch, clinician and time; API validates scope, eligibility and conflicts. 
15. Appointment is created as the approved initial status (for example requested or confirmed; final status choice is open). 
16. Authorized staff may confirm, reschedule, cancel or check in according to state-transition rules. 
17. Each transition is audited and triggers only approved in-app/email notifications. 
18. On completion, the appointment can link to a clinical encounter if that workflow is approved. 
11.4 Clinical note lifecycle 
19. Clinician opens an assigned appointment/patient chart and passes clinical-read permission and resource-scope checks. 
20. Clinician creates a draft note and may add approved diagnoses/vitals/prescription data. 
21. Authorized clinician saves the draft; draft remains editable within policy. 
22. Signing requires a distinct permission; the API records signer and timestamp and makes the signed version immutable. 
23. Correction after signing creates a linked amendment/version with author, timestamp and reason; the original remains 
auditable. 
24. Patient portal visibility is denied until an explicit release policy is approved. 
11.5 Laboratory workflow 
25. Authorized clinician creates a lab order tied to patient, ordering user and facility. 
26. Lab technician views orders in assigned scope and updates permitted sample/work statuses. 
27. Lab technician enters result values and units; validation rules depend on test catalog design. 
28. If verification is enabled, a separately authorized verifier reviews and signs off the result. 
29. All edits/corrections preserve author, timestamps and previous result versions. 
30. External laboratory transmission is excluded from this release. 
11.6 Invoice and manual payment recording 
31. Billing user creates a draft invoice with line items and amounts. 
32. API validates currency, arithmetic, patient/facility scope and permitted billing rules. 
33. Authorized user issues the invoice; issued invoice becomes immutable except through approved correction/void process. 
34. Billing user records a manual payment against the invoice; API validates positive amount and outstanding balance according to 
policy. 
35. System calculates invoice balance from posted transactions rather than trusting a client-submitted balance. 
36. Payment gateway, insurance claims and automatic refunds are not included in this baseline. 
11.7 Patient nearby-facility discovery 
37. Patient opens discovery and chooses to enter an area/address or explicitly selects Use my location. 
38. If browser location is granted, the UI sends the coordinates to the approved search flow; if denied/unavailable, manual search 
remains usable. 
39. Search service queries only active, approved, publicly listed facilities with valid coordinates/address data. 
40. UI displays result cards and map markers with public-approved fields only. 
41. Patient can open a facility detail page; appointment booking is shown only if the booking policy is approved and implemented. 
42. Map-provider errors produce a usable list/manual-search fallback where available; no sensitive patient data is sent to the maps 
provider.

11.8 Role assignment and audit 
43. Administrator opens a user and selects a role, scope and optional start/expiry dates. 
44. API verifies the administrator can delegate every permission included in the role and that the scope is within their authority. 
45. Assignment is written transactionally with an audit event. 
46. Authorization version/cache is invalidated; access changes apply promptly. 
47. Revocation ends the assignment and may revoke sessions for high-risk privilege removal. 
48. Audit viewers can filter and export only within their audit permissions; audit rows are not editable.

21.3 Integrity, indexes and transactions 
• Use UUID primary keys consistently if following the source SQL example. 
• Use foreign keys and organization-aware constraints where feasible; validate that all referenced entities belong to the same 
organization in service logic and, for high-risk relationships, through composite constraints. 
• Unique lower(email) within organization for staff accounts, as stated in the source baseline. Patient identity uniqueness rules 
remain open because duplicate patients may not share email/phone. 
• Indexes should support common filters: organization_id + status; facility_id + appointment start time; patient_id + created_at; 
appointment status/time; invoice patient/status/date; lab status/date; notification recipient/read/created_at; audit 
timestamp/actor/action. 
• Use transactions for role mapping replacement, role assignment/revocation, invoice issuance, payment recording/reversal, 
clinical signing/amendment and lab verification. 
• Never calculate financial balance from a client-submitted total; derive from persisted invoice items and posted 
payment/reversal ledger rows. 
• Use optimistic concurrency/version fields for high-conflict updates where needed. 
• Define retention, backup, restore and archival policies before production.

23. API conventions and validation 
• Use JSON request/response bodies and ISO 8601 timestamps. Store timestamps as timestamptz and render in the facility/user 
timezone as appropriate. 
• Use cursor or page-based pagination with bounded page size; return total counts only when necessary and safe. 
• Use DTOs/allowlists per operation so clients cannot mass-assign organization_id, created_by, signed_at, role flags or audit 
fields. 
• Use PATCH for partial updates and POST action endpoints for state transitions such as sign, verify, cancel, issue and reverse. 
• Return 401 for missing/invalid authentication, 403 for authenticated but unauthorized requests, 404 for missing or deliberately 
undisclosed resources, 409 for conflicts, 422 for business rule violations and 429 for rate limits. 
• Validate input with a schema library; normalize email/phone/address as appropriate; reject unknown fields on sensitive 
endpoints. 
• All list endpoints must apply tenant and facility scopes before pagination and aggregation, not filter only after results are 
fetched. 
• API versioning and deprecation policy should be documented before public integrations are released.

25. Security, privacy and audit design 
• Authentication proves identity; authorization determines what the identity may do. Never infer permission solely from a 
frontend role label. 
• Derive organization context from the authenticated session and validate requested branch/facility context against active 
assignments. 
• Use deny-by-default; explicit deny overrides allow; check assignment expiry, user/org status, resource scope and contextual 
policy. 
• Protect against IDOR and cross-tenant access by scoping every repository query and verifying ownership of nested resources. 
• Use secure session handling, refresh rotation/reuse detection, rate limits and revocation. Apply stronger authentication to 
privileged roles as a future/approval decision. 
• Audit role changes, permission changes, assignment/revocation, denied high-risk actions, sensitive clinical access, note 
signing/amendment, lab verification, invoice issue/void, payment reversal and exports. 
• Audit events should include actor, organization, action, resource identifier, timestamp and request ID; IP/user agent may be 
included subject to privacy policy. Do not include passwords, tokens or full clinical content. 
• Keep audit rows append-only at application level; restrict access to audit viewing/export and define retention. 
• Use encryption in transit and encrypted backups/storage according to deployment controls; manage secrets outside source 
control. 
• Define least-privilege database credentials, migrations, backup/restore drills, vulnerability updates and incident response.

30. Definition of done 
• Every protected endpoint declares the required permission and applies organization/facility/resource scope. 
• All selected screens have documented controls, form fields, validation, success/error states and permission requirements. 
• Role and permission changes are transactional, audited and invalidate cached authorization. 
• System roles and permissions are seeded through version-controlled migrations. 
• Clinical signing/amendment and financial posting/reversal preserve traceability. 
• Maps and email integrations fail safely and do not leak credentials or protected data. 
• Automated tests cover allow, deny, expiry, ownership, cross-tenant and cross-facility scenarios. 
• No sensitive data is exposed in logs or generic error responses. 
• Product decisions affecting portal access, appointment booking, branch sharing, clinical content and retention are approved. 
• Security, backup/restore, monitoring and operational readiness reviews are completed before production.
